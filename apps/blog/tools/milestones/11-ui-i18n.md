# Milestone 11-ui-i18n: Translate the UI chrome (drawer, toolbars, settings popover, view labels)

STATUS: NEXT (authored 2026 at the close of 11-language-persist, per the
human's request; NOT yet started). This is a MISSING-FEATURE milestone, not a
regression — no UI-chrome i18n was ever implemented.

Predecessors: 11a (translation pipeline + switcher), 11-language-persist
(language persistence; the switcher + persisted language now work). Sibling
track: 11b-b (CONTENT translation, quota-blocked — separate; this milestone is
about the app CHROME, not the post bodies).

## Why this exists

Reported by the human: switching language does NOT change the text inside the
Settings (gear) popover. Verified: NOTHING in the app chrome is translated —
there is no i18n module and no `data-i18n` markup anywhere. The Settings
popover, the drawer (Menu / Language / Theme / Font + their option labels), the
bottom toolbar labels, and the view strings ("Read full post", "No posts
found", the 404 page) are ALL hardcoded English. What DOES already follow the
language: the drawer switcher's own selection, the toolbar language menu
hrefs/mirror, and the TTS **Voice** `<select>` CONTENTS (populateVoices runs on
setLang). The chrome STRINGS are the gap.

## Objective

When this milestone is done: every USER-VISIBLE chrome string renders in the
CURRENT route language (en/fa/th/ar), updates on language change, and degrades
to EN when a string has no translation. Post BODY text is unaffected (that is
11b-b). Switching to fa/th/ar shows localized controls; switching back to en
restores English.

## Scope (text vs structure)

IN SCOPE (chrome strings; the app's own labels — NOT post content):
- Settings popover: "Speed", "Fine", "Pitch", "Natural pitch (auto)",
  "Manual", "Voice", "Test voice", "Default voice", "Voice unavailable", the
  "Custom (…)" pattern, the speed-step NAMES (Slower/Slow/Normal/Fast/Faster),
  the popover's own aria-labels, "Loading voices" if present.
- Drawer: "Menu", section labels "Language"/"Theme"/"Font", the option labels
  if they are chrome (English/فارسی/ไทย/العربية are ENDONYMS and likely stay
  as-is — decide; Theme Light/Dark/Auto and Font Default/Traditional/Modern
  ARE chrome and must translate).
- Toolbar: the transport button aria-labels (Play/Pause/Stop), the settings /
  language / font icon aria-labels, the language-menu items.
- Views: "Read full post" (10b residual, if still present), "No posts found" /
  "Try another language." (renderList), the 404 page ("404", "Post not found.",
  "Back to home"), the feed/loading error text ("Failed to load blog data."),
  the list panel title "Two Legs Bad" (DECIDE: this is the blog's NAME — likely
  NOT translated).
- `<html lang>`/`dir` already handled by the router; the document `<title>` if
  present.

OUT OF SCOPE:
- Post bodies (11b-b), the extraction seam (import-post.js, frozen D-Tool-29),
  content/**, feed.json, renderer.js block output, router.js route vocabulary.
- RTL/typography FINE-TUNING (12a/12b own that); this milestone only needs the
  string set to be RTL-SAFE (no CSS work beyond what already exists).

## Interfaces (to be finalized at the START of the milestone chat)

Proposed (subject to the milestone chat's own recon):
- NEW module assets/js/i18n.js -> window.BlogI18n = { t(key, lang?), lang, setLang,
  apply(root), onChange }.
  - A DICTIONARY: { en: {...}, fa: {...}, th: {...}, ar: {...} } keyed by stable
    string KEYS (e.g. "settings.speed", "settings.testVoice",
    "toolbar.play", "view.backToHome", "drawer.menu").
  - t(key, lang): the string for lang, falling back to en, then to the key
    itself (so a missing translation is VISIBLE, never blank).
  - apply(root): walk `[data-i18n]` (+ `[data-i18n-aria]` for aria-labels) and
    set textContent / attributes for the current lang. This keeps the FIXED
    markup in index.html English (the source of truth) while the runtime swaps.
- index.html: add `data-i18n="<key>"` to every chrome element; load i18n.js in
  <head> (pre-controller, like lang.js/theme.js/font.js) OR in the body before
  app.js (DECIDE; no parse-time flash concern for chrome).
- app.js: on every route change, call BlogI18n.setLang(route.lang) +
  BlogI18n.apply(document) AFTER the view render (so dynamically-built labels
  are localized too). Guarded (no-op when BlogI18n absent).
- speech-settings.js: the DYNAMIC strings it builds (speed-step option labels,
  "Custom (…)", "Default voice", "Voice unavailable") must read from BlogI18n
  at build time (guarded; byte-identical when absent). populateVoices /
  mirrorRate need to re-render their option labels on setLang.
- tts.js: transport aria-labels if they are set from JS (DECIDE; else index.html
  data-i18n covers them).

## Decisions to freeze IN THAT CHAT (candidates)

- D-11i-1: dictionary shape + key naming; en is the source; missing key falls
  back to en then to the raw key (never blank).
- D-11i-2: markup strategy: `data-i18n` on fixed index.html nodes; JS-built
  strings read BlogI18n.t() at build time.
- D-11i-3: endonyms (English/فارسی/ไทย/العربية) and the blog NAME "Two Legs
  Bad" are NOT translated (decide explicitly).
- D-11i-4: applied AFTER route render so dynamic labels localize; on language
  change too.
- D-11i-5: graceful degradation — absent BlogI18n or an unknown lang leaves EN
  chrome fully functional.
- D-11i-6: no i18n leakage into the seam/content/feed.json/renderer; guarded
  reads everywhere (tts/speech-settings behave byte-identically when absent).
