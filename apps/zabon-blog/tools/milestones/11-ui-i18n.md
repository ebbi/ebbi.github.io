# Milestone 11-ui-i18n: Translate the UI chrome (drawer, toolbars, settings popover, view labels)

STATUS: NEXT (authored 2026 at the close of 11-language-persist, per the
human's request; NOT yet started). This is a MISSING-FEATURE milestone, not a
regression — no UI-chrome i18n was ever implemented.
track: 11b-b (CONTENT translation, quota-blocked — separate; this milestone is
about the app CHROME, not the post bodies).

## Why this exists

Reported by the human: switching language does NOT change the text inside the
Settings (gear) popover. Verified: NOTHING in the app chrome is translated —
there is no i18n module and no `data-i18n` markup anywhere. The Settings
popover, the drawer (Menu / Language / Theme / Font + their option labels), the
bottom toolbar labels, and the view strings ("Read full post", "No posts
found", the 404 page) are ALL hardcoded English. What DOES already follow the
language: the drawer switcher's own selection, the toolbar language menu
hrefs/mirror, and the TTS **Voice** `<select>` CONTENTS (populateVoices runs on
setLang). The chrome STRINGS are the gap.

## Objective

When this milestone is done: every USER-VISIBLE chrome string renders in the
CURRENT route language (en/fa/th/ar), updates on language change, and degrades
to EN when a string has no translation. Post BODY text is unaffected (that is
11b-b). Switching to fa/th/ar shows localized controls; switching back to en
restores English. **DONE + browser-verified.**

## Interfaces (FROZEN)

- NEW module assets/js/i18n.js → window.BlogI18n = { t(key, lang?), lang
  (live getter), setLang(code), apply(root, lang?), onChange(cb) }.
  - A DICTIONARY { en, fa, th, ar } keyed by stable string KEYS (namespaced
    settings._ / speed._ / drawer._ / theme._ / font._ / toolbar._ / view._ /
    menu._ / lang._ / brand._). en is the source of truth; 44 keys.
  - t(key, lang): lang → en → the key itself (never blank).
  - apply(root): walk `[data-i18n]` (textContent) + `[data-i18n-aria]` (the
    NAMED attribute; the key comes from the sibling `data-i18n-key`).
  - setLang(code): sets the current language, fires onChange listeners; an
    unknown code resolves to en (D-11i-5).
- index.html: `data-i18n`/`data-i18n-aria` on every chrome element; i18n.js
  loaded in <head> AFTER lang.js (pre-controller, no parse-time side effect).
- app.js: handleRouteChange calls BlogI18n.setLang(route.lang) BEFORE the view
  render (D-11i-8) + BlogI18n.apply(document) AFTER syncSpeechForRoute; the
  JS-built 404 / no-posts / error / blogTitle strings read a guarded t().
  Graceful fallbacks flip the copy to the LOCALIZED string ONLY when BlogI18n
  is present; the English fallback keeps byte-identical behavior when absent.
- speech-settings.js: the DYNAMIC strings it builds (voice option labels,
  "Custom (…)", the lang-button aria) read a guarded tr(); a BlogI18n.onChange
  listener re-localizes them on language change.
- tts.js: UNCHANGED — it sets no aria/text strings from JS (the transport
  aria-labels are fixed markup, covered by data-i18n-aria). Byte-identical.

## Decisions FROZEN

- D-11i-1: dictionary shape + key naming; en is the source; missing key falls
  back to en then to the raw key (never blank).
- D-11i-2: markup strategy: `data-i18n` (+ `data-i18n-aria`/`data-i18n-key`)
  on fixed index.html nodes; JS-built strings read BlogI18n.t() at build time.
- D-11i-3: endonyms (English/فارسی/ไทย/العربية) are NOT translated.
- D-11i-4: applied on every route change; setLang runs BEFORE the view render
  (see D-11i-8), apply(document) AFTER; onChange re-localizes JS-built strings.
- D-11i-5: graceful degradation — absent BlogI18n or an unknown lang leaves EN
  chrome fully functional; all call sites guarded.
- D-11i-6: no i18n leakage into the seam/content/feed.json/renderer; guarded
  reads everywhere (tts/speech-settings behave byte-identically when absent).
- D-11i-7 (human-requested): the toolbar BRAND ("Zabon Blog" → brand.title) AND
  the list-panel blog title ("Two Legs Bad" → brand.blogTitle) ARE translated.
- D-11i-8 (ORDERING bug fix): setLang MUST precede the view render because the
  JS-built view strings read t() at build time; reversing the order made the
  view lag one language behind (the reported fa-title-in-EN bug).
