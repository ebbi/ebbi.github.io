## Objective

When this is done: `import-post.js` models the class

  `<p style="text-align:justify;">...prose...<img ... /></p>`
  (a bare `<p>` whose content is PROSE followed by a single trailing
  `<img>` at the END of the same `<p>`)

so that (a) the inline `<img>` is no longer leaked into paragraph text
(`img_para_leftover = 0`) and (b) the trailing image is no longer
silently dropped (raw `<img>` count == rendered image-block count). The
recon of series part-2 then becomes seam-ready
(`{image:21,paragraph:53,embed:2}`, 76 blocks, all `*_para_leftover = 0`),
and every previously shipped `content/en/*.json` (21/21) still re-extracts
byte-identically.

## Known issues the next chat must NOT mistake for bugs

- The `imageBarePProse` regex uses a TEMPERED dot
  (`(?:(?!<\/p>)[\s\S])*?`) for the leading run. This is DELIBERATE: it
  bounds the match to the SAME `<p>` so it can never span from the first
  bare `<p>` in the body to a later `<img>`, swallowing every block
  between. Do not "simplify" it to `[\s\S]*?`.
- A leading-`<img>` `<p>` (D-Tool-24 shape) is NOT this class; ties
  resolve to the earlier TOP entry (D-Tool-24). Both entries can match a
  `<p>` that has both a leading and a trailing `<img>`; D-Tool-24 wins,
  and its trailing prose will then contain the second `<img>` markup —
  such a double-`<img>` `<p>` has NOT been observed and is NOT in scope.
- The `src` for a `<p>` with BOTH a leading and trailing `<img>` would be
  the FIRST `<img>` (attrOfFirst); not in scope (see above).
- The recovery is a SILENT-loss shape: a DROPPED image class is invisible
  to `*_para_leftover`; ALWAYS reconcile raw `<img>`/`<iframe>` counts
  (warn #9).
